# Design

## Context

Мотивация и замеры — в `proposal.md`, требования — в `specs/`. Что известно:

- Прошлый change (`optimize-reactive-props`) привёл свойства к `Prop`/`OptProp` и убрал `Memo`; при SSR замыкания атрибутов почти бесплатны (5 аллокаций против 4 у готовых строк), а вот в браузере каждое замыкание-атрибут — `RenderEffect` (≈ 0,5 КБ). У кнопки их ≈ 12: итого 6,7 КБ линейной памяти wasm на экземпляр против 0,33 КБ у иконки (замер на 1000 экземпляров, release).
- Единым значением «строка или замыкание» атрибут выразить нельзя: `Either` не реализует `AttributeValue`, `AnyAttribute` дороже (7 аллокаций против 5). Рабочий вариант — ветвление на уровне всей разметки: `Either<A, B>` реализует `Render` и `RenderHtml`, значит компонент может вернуть разные `view!` в зависимости от статичности свойств.
- В `view!` идентификатор перед `{..attrs}` нужно оборачивать в `{}` (иначе макрос читает его как литерал структуры).

## Goals / Non-Goals

**Goals:**
- Статические Badge/Button не создают `RenderEffect` на атрибуты и блоки.
- Ветви не расходятся: разметка пишется один раз, тесты гоняют обе ветви.
- Цель по памяти: ≤ 3 КБ на статическую кнопку (было 6,7 КБ) — проверяется спайком в первой группе задач (go/no-go).

**Non-Goals:**
- Размер wasm-бинарника, остальные компоненты, смена API.

## Decisions

### D1. Выбор ветви при создании экземпляра
`let is_static = props.all_static();` (все `Prop::is_static()`; `ViewFn`, `children` и `pt` статичны всегда). Дальше `if is_static { Either::Left(static_view) } else { Either::Right(dynamic_view) }`. Решение принимается один раз: если свойство позже окажется сигналом, пересоздаётся весь экземпляр, а не ветвь.

### D2. Разметка один раз — через `macro_rules!`
Макрос `button_markup!` принимает выражения атрибутов и блоков (`$class`, `$style`, `$disabled`, `$content`, …) и разворачивается в один `view!`; статическая ветвь передаёт готовые значения (`String`, `Option<&'static str>`, `bool`), реактивная — `move ||`-замыкания. Расхождение ветвей по структуре исключено: меняется только тип выражений.
*Альтернативы*: два вручную написанных `view!` (расходятся со временем); общий `Either`-атрибут (не компилируется, D-контекст); `AnyAttribute` (дороже).

### D3. Статические значения считаются один раз
В статической ветви состояние и строки (`class`, `data-p`, `style`, `type`, `aria-label`, `tabindex`) вычисляются разово в начале; блоки (иконка или индикатор, метка, бейдж) — обычные `Option<View>`, а не замыкания. Для Badge то же.

### D4. Проверка паритета
Параметризованные тесты: каждый сценарий SSR (`ssr.rs`) выполняется дважды — со статическими значениями и с теми же значениями через `RwSignal` — и сравнивает HTML. Браузерные тесты событий выполняются в обеих ветвях.

### D5. Измерение
`e2e/tests/memory.spec.ts` получает сценарии «статические кнопки» и «реактивные кнопки» (одна из них передаёт `loading` сигналом); в `docs/benchmarks.md` записываются обе строки.

## Risks / Trade-offs

- [Два экземпляра разметки в бинарнике: рост wasm на +5–15 % вклада] → замеряем `wasm-size`, пересматриваем бюджеты.
- [Статический путь не доходит до цели ≤ 3 КБ] → спайк (задача 1.2) с критерием go/no-go: если прирост < 40 %, change сворачивается, результат записывается в `docs/benchmarks.md`.
- [Макрос усложняет чтение] → одна пара макросов на компонент, комментарий, как добавлять атрибут; правило для следующих компонентов — в `docs/button.md`.
- [Реактивное свойство, добавленное позже, неожиданно меняет ветвь] → ветвь выбирается по `Prop`, документировано; поведение обеих ветвей одинаково по тестам.

## Migration Plan

Миграции нет: публичный API и разметка не меняются. Откат — `git revert`. Бюджет размера wasm в `benches/budgets.toml` пересматривается после измерения.
