# Design

## Context

Мотивация и таблица замеров — в `proposal.md`, требования — в `specs/`. Что выяснено:

- `exp-raw`: «голый» `<span class data-p>` ×1000 = 2 аллокации на экземпляр; `Pt::new().merge_class()` + `attrs()` добавляют 0; одно `Memo` — +9; одно `MaybeProp<String>` (из значения) с чтением в замыкании — +3.
- Badge: 5 свойств (`value`, `severity`, `size`, `badge_disabled`, `style_class`) + `Memo<BadgeState>` + `class_memo` ≈ 41. Button: ≈ 25 свойств-сигналов + два `Memo` ≈ 67. Это согласуется: стоимость почти целиком — реактивные примитивы свойств, а не разметка.
- `Signal<T>` и `MaybeProp<T>` по умолчанию (`#[prop(optional)]`) тоже создают записи в арене на каждый экземпляр.
- В браузере (CSR/hydrate) каждое атрибутное замыкание в `view!` создаёт `RenderEffect` даже без зависимостей; при SSR замыкание выполняется один раз без примитивов.

## Goals / Non-Goals

**Goals:**
- Статический Badge/Button не создаёт реактивных примитивов ни при SSR, ни в браузере.
- Сохраняется совместимость вызова (`value="5"`, `loading=signal`, `severity=ButtonSeverity::Danger`), поведение и все существующие тесты.
- Шаблон, которому будут следовать остальные компоненты: `Prop<T>` + статический быстрый путь.

**Non-Goals:**
- Размер wasm (отдельно: `opt-level`, `wasm-opt`, состав web-sys features).
- Изменение API компонентов, спек поведения и разметки.

## Decisions

### D1. Тип `Prop<T>` в `prime-core`
```rust
pub enum Prop<T> { Static(T), Reactive(Signal<T>) }
```
Конструкторы через `From`: `T` → `Static`; `Signal<T>`, `ReadSignal<T>`, `RwSignal<T>`, `Memo<T>` → `Reactive`; для строк — `&str` → `Prop<String>`. `Default` — `Static(T::default())`. Методы: `get()` (отслеживающее чтение; для `Static` — клон), `get_untracked()`, `is_static()`. Для необязательных значений — псевдоним `OptProp<T> = Prop<Option<T>>` с `From<T>` (`Some`). Коэрсия `From<T> for Prop<T>` и `From<Signal<T>> for Prop<T>` не пересекаются (T не может равняться `Signal<T>`); для `Prop<Option<U>>` аналогично по occurs check. Если компилятор откажет, `OptProp<T>` станет отдельным типом.
*Альтернативы*: `MaybeSignal` из Leptos (в 0.8 удалён, заменён `Signal` с арена-записью даже для значения); дженерики на компонент (`Badge<V: Into<...>>`) — ломают вывод типов и `view!`.

### D2. Статический быстрый путь
Компонент вычисляет `all_static` один раз (все `is_static()`). Атрибуты строятся так: если все статические — готовая `String`; иначе — реактивное замыкание. Обе ветки выражаются одним значением через `leptos::either::Either<String, impl Fn() -> String>`, которое реализует `AttributeValue`: разметка в `view!` одна. Для статического пути в браузере не создаются `RenderEffect`, при SSR нет арена-записей.
*Альтернатива*: всегда замыкания (проще, но в браузере `RenderEffect` на каждый атрибут каждого экземпляра).

### D3. Без `Memo` и `class_memo`
`BadgeState`/`ButtonState` собираются в замыкании (`let state = move || State { … props.get() … }`), классы и `data-p` — функции от состояния, вызываемые в атрибутных замыканиях. Лишних обновлений DOM нет: Leptos не перезаписывает атрибут, если строка не изменилась (проверяется тестом «class не перезаписывается»). Для динамического пути `Memo` одного состояния остаётся допустимым (один на экземпляр вместо трёх), если замеры покажут выгоду; решается в задаче 3.2.

### D4. Бюджеты аллокаций
`benches/alloc-budgets.toml`: `max_blocks_per_instance` для `badge`, `button`, `button-full`; команда `cargo xtask alloc-budget` читает `target/bench/alloc.json` и падает при превышении (как `wasm-size`). Целевые значения определяются измерением после миграции (с запасом ≈ 20 %); ориентир — не более 12 для Badge и 25 для Button.

### D5. Проверка в браузере
Сценарий памяти из `e2e/tests/memory.spec.ts` (1000 иконок) дополняется сценарием «1000 Button»; `browser.mount-*.heap_bytes` и `dom_nodes` сравниваются до и после.

## Risks / Trade-offs

- [Дополнительный тип `Prop` усложняет сигнатуры и подсказки IDE] → единый тип во всех компонентах, документированные примеры; `Into` сохраняет вид вызова.
- [Коэрсии `Prop<Option<T>>` могут не скомпилироваться из-за правил когерентности] → отдельный `OptProp<T>`, см. D1.
- [Статический быстрый путь удваивает код вычисления атрибутов] → один helper `attr(all_static, f)` в `prime-core`, тесты на обе ветки.
- [Регресс реактивности] → существующие тесты реактивности (SSR и браузерные) остаются неизменными и обязаны пройти.

## Migration Plan

Миграции для пользователей нет: исходный вызов совместим. Откат — `git revert`. Бюджеты аллокаций включаются в CI после появления новых значений.
